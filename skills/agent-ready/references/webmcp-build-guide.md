# WebMCP build guide (field notes)

What was learned building, testing and shipping WebMCP tools on live sites: six WordPress builds (five plugins, with 15, 13, 11, 10 and 7 tools, and a mu-plugin) and one Next.js build. Everything here was seen in practice between October and November 2026. Version numbers and trial dates move, so re-check them before quoting.

Read this when the user wants to build, review, test or ship WebMCP tools. Build them when the site has a visitor journey an agent could serve: find a location, get a price range, search products, start a request. For making a site readable for AI agents in general (robots.txt for AI bots, llms.txt, Markdown for agents, MCP Server Cards), use the agent-readiness skill ([github.com/Pacamaraprogress/agent-readiness](https://github.com/Pacamaraprogress/agent-readiness)).

## 1. Status and reach (checked November 2026)

- WebMCP lets a page register tools for an AI agent running in the visitor's browser. API entry point: `document.modelContext`, the only one the spec defines. Reading `navigator.modelContext` as a fallback is harmless, but no current source uses it. `getTools()` lists tools; `executeTool()` returns a JSON **string**.
- Since 19 Nov 2026 (spec; webmcp-types 0.2.0, 20 Nov) `getTools()` returns read-only `Tool` objects in place of the old `RegisteredTool` dictionaries. This changes agent and test code, not how a page registers tools. In test scripts, read the fields by name: a missing `inputSchema`, `outputSchema` or `annotations` is now `null` (so keep `t.annotations || {}`), and the owner window is `source` (`window` is expected to go with Chrome 160). A `Tool` has no `toJSON`, so `JSON.stringify(tool)` or returning the tool itself from `page.evaluate` gives an empty object: map it to the fields you need. A `Tool` held from before the tool was registered again fails with `NotFoundError`, so call `getTools()` again rather than keeping tools across a page change. The Chrome team's list (24 Nov 2026) puts it in 160.0.8173.0 (Canary), so it is expected to reach Stable with Chrome 160 on 5 Jan 2027 (Chrome 160's planned Stable date); until then read `tool.source ?? tool.window`. Also `{...tool}` copies nothing and `structuredClone(tool)` throws. Chrome 158.0.8127.88 (seen 24 Nov) already gives `Tool` objects: `JSON.stringify(tool)` is "{}", `structuredClone(tool)` throws `DataCloneError`, and `executeTool()` refuses a tool name with `TypeError`. It still names the owner `window`, and it has no `outputSchema` field at all (`undefined`, not `null`). The five answer-shape checks pass on it. The team expects the API shape to change a lot before it ships in early 2027, so check the list before each release.
- Chrome runs it as an origin trial (Chrome 149 to 162). Without a token, Chrome's documented route for local testing is `chrome://flags/#enable-webmcp-testing` ([Chrome docs](https://developer.chrome.com/docs/ai/webmcp)). For automated tests (puppeteer, headless), start Chrome with `--enable-features=WebMCP`; in our tests the `--enable-features=WebMCPTesting` switch alone was not enough.
- Chrome, Edge and Brave 157 all expose it behind the flag, none by default. Edge has its own origin trial with its own token; in tests Edge and Brave also honoured a valid Chrome-issued token.
- Brave's own assistant, Leo, uses WebMCP tools by default from Brave 1.102.2, which Brave expects on 5 January 2027 (spec's implementation-status page, 12 Nov 2026). From then on Leo calls a site's tools with no test flag on the visitor's side ([spec PR #383](https://github.com/webmachinelearning/webmcp/pull/383)), so test client sites in Brave with Leo after that release. Edge runs its own origin trial in Edge 150.
- WebKit's standards position is "oppose", Mozilla's is "neutral". Plan for Chromium only.
- Official polyfill `@w3c/webmcp-polyfill` (W3C, Apache-2.0; 0.2.0 on 23 Nov 2026, announced by the Chrome team on 24 Nov). In a secure page with no `document.modelContext` it adds one. It never adds `navigator.modelContext` and never replaces a native context, even a partial one. It follows webmcp-types 0.2.0: `getTools()` gives `Tool` objects and shows `outputSchema`. `executeTool()` takes a `Tool` from `getTools()` plus an input object and returns a JSON string; a tool name is refused with `TypeError`. Every reference build's test scripts already pass the `Tool` (`(await getTools()).find((t) => t.name === name)`). Like the spec it refuses a duplicate name, a name outside 1 to 128 of `A-Z a-z 0-9 _ - .`, and an empty description. It checks neither inputs nor answers against the schemas. Imperative API only: no declarative forms, no `resumeTool()`. No browser agent sees its tools (that needs the browser's own support), so never ship it on a client site. If a theme or another plugin loads it before our loader, the loader's `modelContext` check passes in every browser, and the tools file downloads for every visitor. When page speed drops, look for it in the page source. Types: `webmachinelearning/webmcp-types`.
- Google's example agent (GoogleChromeLabs/webmcp-extension) runs tools marked `readOnlyHint` without asking the user and asks before the rest.
- Chrome 157 rejects a second `registerTool` with a name already registered (`InvalidStateError`, "Duplicate tool name"). Guard the script so it starts once, and only in the top page: a page shown in a frame (an embed, a lazy-loaded form) should download nothing and register nothing. The spec (11 Nov 2026) also says `getTools()` gathers tools from the whole tab: tools that an allowed frame in the same tab registers can sit in the agent's list beside the page's own. One more reason to register in the top page only.
- Spec PR #373 (merged 24 Nov 2026) adds `document.modelContext.waitForToolsUntil(promise)`. A page that registers its tools after an async step (a loader that downloads the tools file after the page loads, a fetch for settings) passes that promise, and the browser's agent waits until it settles, or until a timeout the browser sets, before it reads the page's tools. Several promises can be given; the tools count as ready once all of them have settled. Wiring it into `getTools()` is left to a later PR, and the implementation-status page does not list it yet (checked 26 Nov 2026). Once a browser ships it: call it only when it exists (`typeof document.modelContext.waitForToolsUntil === 'function'`), pass the promise of the whole registration, and test that every tool still registers in a browser without it.
- Chrome's "WebMCP tool security" page gives size guidance (checked 14 Nov 2026): about 1,500 characters per tool answer, 500 per tool description, 150 per parameter description, 30 per tool or parameter name. It is guidance, not a limit Chrome enforces.
- PageSpeed Insights (Lighthouse 13.6+) has an "Agentic browsing" group that lists the page's tools once a valid token is on the page. Without a token the audits show "Not applicable".
- The tools have no address, so nothing made for promoting an MCP server applies to them: no connect link, server card, catalog entry or registry listing. An agent finds the tools by opening the page. The spec group has open proposals for announcing a site's tools before a visit (issues 340 and 341, both open on 18 Nov 2026); none is adopted. A plain description of the tools in `llms.txt` or on a page is the only thing a site can add today, and no agent is known to act on it. A remote MCP server, which does have an address, is a different thing; the agent-readiness skill covers how to list and promote one.

**Say this plainly to the site owner:** WebMCP tools do not change Google rankings. Their value is that an agent visiting the site gets correct answers and is routed to the right page or form.

## 2. Tool design rules

1. **Design a funnel, not a list.** Decide the journey first (see work, read the process, read an article, get a price range, find the location, start a request), then one tool per step.
2. **Read-only tools first.** Most tools should only read. Keep write-like tools to the one or two that matter (a lead form, a catalog request).
3. **Never submit for the user.** A form tool opens the right page, fills the fields, shows a visible banner, and stops. The person ticks the CAPTCHA and presses send. The result says what was filled (`will_fill`) and what is still empty (`still_needed`).
4. **Cross-page hand-off:** store the request in `sessionStorage`, navigate, fill on arrival. The spec has a built-in way coming, *continuations*: the tool calls `options.invocation.requestToken()`, passes the token to the next page in its address, and that page calls `document.modelContext.resumeTool(token, callback)`. The callback gets the original input and what it returns is the tool's answer, so the agent hears back from the form page. Rules in Chromium (explainer updated 13 Nov 2026 to match the code): same origin (not only the same site: a move between subdomains fails), same tab, one token per call, redeemed within 30 seconds. It needs no storage, so it would also cover rule 15. Check that the origin trial includes it before building on it, and keep `sessionStorage` as the fallback for browsers without it.
5. **Imperative JavaScript tools beat declarative form attributes** for real forms. In Chrome 157 a declarative `toolname` form exposes a CSS-hidden text field (a spam trap) as a tool parameter; only `type=hidden` is skipped. Form plugins also rename fields per form.
6. **Keep answers small.** Set an output budget in one constant (Chrome's guidance is about 1,500 characters; 2,000 was used before), clip at whole sentences, cap lists at four or five items, and always give the page address for more. See "Spending the answer budget" below.
7. **Echo what was understood:** `query_used`, `filters_applied`, `total_matching`. An agent that cannot see how its question was read will guess.
8. **Errors are answers.** Return a code, a plain message, and the choices (for example the list of matching locations for an ambiguous name). Mark input mistakes `retryable: false`; only real temporary failures are retryable. Check the shared helper, not one tool: one plugin's `fail()` said `retryable: true`, so all 18 of its input errors invited the same failing call again.
9. **Free text in, checked in code.** Accept loose wording ("quartz", "12 by 14 feet") and validate in code rather than forcing strict enums that agents get wrong.
10. **Parse sizes carefully.** Units can be written out or attached ("3 meters x 4 meters", "4m x 5m", "10'6\" x 12'"). Test the parser on a table of real wordings; silent wrong numbers are worse than an error.
11. **One fact, one source.** If the business has a fixed fact that old pages state wrongly (a location count, a founding year), normalise it in quoted text in one place in the tools, and test that rule against the exact wordings found on the live pages (for example "12 locations in 5 states" next to "12+ locations").
12. **Tool descriptions say when to use the tool and what comes back,** in one or two sentences. Do not put instructions to the agent about the user in them. Keep each under 500 characters and test it: a description that lists topics grows with every topic added (one stood at 493).
13. **A `next` step names only tools this site registers.** If a tool exists only when a page exists (a loyalty program, a catalog request), build the text from the same setting that registers the tool.
14. **Two forms with the same fields are still two forms.** A catalog request and a contact form can both have name, email, phone and ZIP. Look for each form only on its own page, and give each tool only the inputs its form has.
15. **When the hand-off cannot be stored** (`sessionStorage` refused: Chrome does this when the visitor blocks the site's cookies), say `stored: false`, promise nothing in `will_fill`, and list every field in `still_needed` again. The oldest plugin promised the fill outright while the page opened empty; the two newer ones already moved the given fields from `will_fill` to `still_needed`. With no details given, keep the plain "opening" answer. Test it by making `sessionStorage` throw (section 8).
16. **The banner says what happened.** Called with no details, the tool only brought the form into view: "opened this form", not "filled in this form".
17. **Place names repeat.** "Washington" is a city, a state, and a town in several other states. Rule that worked: alone or with "DC" it is the city; after a comma, whatever follows names the state ("Washington, VA"); a state's name or code right after it does too.
18. **A form embedded from another service cannot be filled.** A form shown in a frame from another site (a CRM's embed) cannot be read or filled by the page's script. The tool opens the page, brings the frame into view, puts a note above it, and says in its answer that the user fills it in (`filled: []`, "cannot be filled in for the user"). If the page also carries a twin form that is hidden on every screen, leave it alone: filling a form nobody sees sends nothing. Say all this in the tool description too, so the agent does not promise the user a filled form.
19. **Find the form the visitor sees by layout, not by markup.** Take the first frame or form that is laid out and wide. Do not ask for its height: an embedded form gets its height from its own script, which can come after the tool runs. Try again a few times after the page has loaded.
20. **One note per form, however often the tool runs.** An embed script moved its frame into a new box about two seconds after the page loaded. The test "is there already a note beside the form" then missed the first note, and a second call added another. Mark the note itself (a data attribute) and look for it on the page.
21. **Where each location has its own form, the form tool needs a location.** A contact page that only lists the locations has no form to fill. Ask for the location (a name, a city or a ZIP code), answer `SHOWROOM_NEEDED` with the list when none is given, and on a location's own page use that page's form.
22. **Two products can share a name.** Check for a second product of the same name before taking the first match, and ask which one is meant, with what tells them apart (the collection) and each one's address.
23. **Contact details come from one place.** A page's old answer named the e-mail address of a location that had closed. The tools give phone numbers and addresses from the location pages only and leave out any guide sentence with an e-mail address in it. Tell the owner about the rule; it is theirs to change.
24. **`outputSchema` is optional: add it only where it pays, and only with a test.** The spec added it on 2 Nov 2026 (webmcp-types 0.1.11). Google's example agent (webmcp-extension, 17 Nov) checks every answer against it and turns any answer that does not match into a tool error that says where it differs. Google's build skill (webmcp-skills, 20 Nov) declares it only on a tool whose answer feeds another tool (a product search whose ids go to a product-details tool) or that gathers many fields into one answer, and leaves it off small single-purpose tools and hand-offs. Errors here are answers (rule 8), so the schema has to cover the failure answers too: `oneOf: [<success schema>, { type: 'object', properties: { error: { type: 'string' } }, required: ['error'] }]`, with no outer `type`, and a success branch that requires its own fields so the two cannot both match. When the answer comes in more than one shape (one item, or a list), give each shape its own branch of the `oneOf`, each requiring its own field: `anyOf: [{ required: ['a'] }, { required: ['b'] }]` inside one branch is refused by Ajv in strict mode, because the required field is not listed in that branch. Test each tool's real answers, good, empty and failed, against it before shipping. Leave it out rather than pass a placeholder: `outputSchema: ''` makes `registerTool` throw a `TypeError`. Since 22 Nov 2026 five of the reference builds declare it: four on their product search and product details tools and nowhere else, and one on a location finder whose answer has two shapes (one location, or every location that matches). Chrome 157 accepts the field but does not use it yet: `getTools()` shows no `outputSchema`, so a test that needs the schema wraps `document.modelContext.registerTool` in the test page and keeps a copy of what each tool registered. Before declaring a field as text, make sure the tool always gives text: one store's search index had a SKU as a number and a category as a list for some products, and a product page had a brand with no name; the tool now turns each into text first.
25. **Keep returning failures as answers; never throw.** Under the spec, a tool that throws or rejects reaches the agent only as a plain `DOMException: OperationError`, with your message, `retryable` and `next` lost (webmcp-skills, 18 Nov 2026). Google's example agent shows what Chrome passes on, cut to 8,000 characters; other agents need not. Throw only where the code has no answer to give (an `AbortError` when the agent stops the call).

### Spending the answer budget

A size limit decides what the agent does not see, so decide it on purpose.

- **Write down what gives way, in order.** In a guide answer: related links down to one, then the page summary, then the third answer. In a product answer: extra guide links down to one (keep one, it is the next step of the journey), then a long opening line, then the last detail lines, with a note that the page has more.
- **Share the room out, best answer first.** A loop that shortens every answer in fixed steps (370, 320, 270…) left three answers of about 115 characters each when the budget went from 2,000 to 1,500. Giving the best answer what it needs, keeping a minimum for the next, and dropping an answer that would be a fragment gave one of 240 to 370 characters plus one or two more. Two readable answers say more than three stubs.
- **Measure every real answer before and after a budget change,** per topic and per product, not only "largest answer is under the limit". The limit passing says nothing about what was lost.
- **A fixed text is part of the budget too.** A price note, a catalog note and a long `next` can take 600 characters before the first answer.
- **Text takes more room in JSON than its length says** (quotation marks). Fit on the serialized size, and keep one last guard.

### The read-only hint

`readOnlyHint: true` means the tool only reads and changes nothing in the page or system. A tool that drives an on-page widget, loads scripts, fills a form or navigates is **not** read-only, even if it "only shows a number". When one tool has two versions (a lookup version on most pages, a version that drives a calculator on one page), only the lookup version carries the hint.

There are two more hints, and all three default to false: write only the ones that are true, never `readOnlyHint: false` (webmcp-skills, 18 and 20 Nov 2026).

- **A hand-off tool carries no hint.** A tool that opens a form or a checkout for the user to finish (rule 3) is not read-only, and it does not take `consequentialHint` either: the user's own click is the confirmation.
- **`consequentialHint: true`** is for a tool that commits something itself, such as placing an order or booking a slot, so an agent can ask the user before running it. Tools built by these rules never commit anything, so none of the reference builds use it.
- **`untrustedContentHint: true`** goes on a tool whose answer carries text written by visitors (reviews, comments, questions and answers). Google's example agent then marks that text as untrusted. Use it too for text from sources the site does not control (feeds, imported reviews). Hints are signals, not guarantees: each agent decides what to do with them, so never rely on a hint alone to stop a hidden instruction or an unwanted action. Text the site's own staff wrote (pages, guides, product copy) does not need it.

### Tool use in analytics

The owner will ask whether agents use the tools. One event per tool call answers it.

- **Wrap in the one place every tool passes through** (`register()`): a wrapper around `execute` that reports once the answer is ready and returns the answer untouched. One wrapper covers every tool, including the ones added later.
- **Send the outcome, never the input.** The tool's name, the outcome (`ok`; `empty` when the tool ran and found nothing, read from `matched === false` or `total_matching === 0`; `error`), the answer's own error code (`CANCELLED` for a call the agent stopped, `EXCEPTION` for a throw) and the plugin version. A question or a form detail can hold a name or a phone number, so nothing asked or typed goes in. Test that: call the tools with a made-up name, phone number and e-mail address and require that none of it appears in any event.
- **Push to `dataLayer`, creating it when it is missing** (`(window.dataLayer = window.dataLayer || []).push(…)`). Tag Manager reads what was queued before it loaded, and on a site that delays scripts it loads late. Set every key on every push (an empty text for "no error"): Tag Manager keeps a key's last value.
- **It must never cost the answer.** Put `try`/`catch` around the push. Compare each answer with the events switched off and require them equal. Give the list a `push` that throws and require the tool to answer anyway. A stopped call still throws its own error.
- **An off switch in the config** (`analytics: false` through the plugin's config filter). No new box on the settings page until someone asks for one.
- **Nothing reaches GA4 until the container has a trigger and a tag.** The site's container and GA4 measurement ID can be found read-only: the page source has the `GTM-` id, and the public `gtm.js?id=GTM-…` file names the `G-` id. Hand over the steps by hand (four Data Layer variables, a Custom Event trigger, a GA4 Event tag, four event-scoped custom dimensions in GA4) and one console line that pushes a test event, so it can be checked without an agent. An import file is a convenience: say when it was not tried in Tag Manager, and write "Merge, never Overwrite" in bold.
- **No access to the site's container is not the end. Look for a Google tag you can edit.** Tag Manager's home lists only "Direct access" until you also tick "Inherited access"; then the Google tags you reach through GA4 or Ads access appear. In 2026 a Google tag is a full Tag Manager container (Workspace, Versions, Submit), and Admin → Container Settings lists every ID it carries. If one of those IDs is a tag the page already loads (a `GT-` tag a WordPress plugin puts on the page, or the `GTM-` id Google now gives a new Google tag), a GA4 Event tag and a Custom Event trigger added there run on the site without the site's own container. "Google-only" containers accept GA4 tags. A Google tag that belongs to an Ads account may be read-only: check before promising it.
- **When nothing can be edited, a footer script can stand in for the tag.** It watches `dataLayer` for the event and pushes a GA4 command (`'event'`, the event name, `send_to` set to the stream, the same values), which the Google tag already on the page sends. It sets a flag so a second copy does nothing, and it also handles events queued before it ran. Put a comment at its top: turn it off if a Tag Manager tag for the event is ever published.
- **Never run the footer script and the tag together.** With both on, one tool call gave three GA4 requests: the tag, the script's command, and the Custom Event trigger firing again on the script's own command. Switch in this order: the owner publishes the tag; test one call (more than one request shows the tag works); set the script to draft; test again (exactly one); check that fresh and cached pages no longer carry the script. The live-check script should know which way each site uses and fail when a site has both or neither.
- **Tag Manager may preselect Overwrite on import.** With it, the preview listed the container's own tag and settings as deleted. Choose Merge, then "Rename conflicting", and read the preview: only "Added" rows, 0 modified, 0 deleted. Stop before Publish; the owner presses it.
- **Count requests in the network log,** one `g/collect` with `en=<event name>` per send, and check each goes only to the expected stream. A plugin like Site Kit sets `ga-disable-<G-id>` for logged-in admins, so an admin browser sends nothing to that stream: test as a visitor, or set the flag to false in the page for one test page view and say so.
- **The live checks send nothing to GA4** as long as they block other hosts. Say so, so test calls are not read as agent use.

## 3. Where the answers come from

Tools should answer from the site's own published content, read live, never from text typed into the plugin.

- **Client-side lookups:** the public WordPress REST API (posts, pages, custom post types). REST `search` can return nothing for a custom post type; filter by taxonomy term instead. Ask for `orderby=relevance`, then re-rank by title yourself: default order is by date and long questions match almost nothing, so retry with the content words only.
- **Server-side knowledge route:** one public REST route that returns sections on demand (`?section=team,financing`), built from the pages themselves and cached. The script asks for all missing sections in one request.
- **FAQ sources, in order:** SEO-plugin schema stored in post meta, then `<details>` or FAQ-block markup, then headings (an h2 "Frequently asked questions" followed by one h3 per question), then the served page as a last resort. Merge when one source is fuller.

Traps met on real sites:

| Trap | What happened | Fix |
|---|---|---|
| Custom permalinks | `get_page_by_path` missed 9 of 16 pages | Build an index of published pages keyed by `get_permalink` path |
| Page builders (Elementor) | Markup is not in `post_content` | Render through `the_content` with the global post set |
| Page builders inside wp-admin | Elementor does not render `the_content` on wp-admin screens, so a settings page that built the knowledge read every builder page from its plain copy, and that reading was cached for visitors' agents | Build nothing in wp-admin and store nothing built there. See "Page builders do not render inside wp-admin" below |
| Archive or template pages | No post behind the address | Read the page as served, mark the entry `source: served` |
| A "hide these questions" list made for structured data | Followed everywhere, so a main guide returned zero answers | Hide lists for schema are not hide lists for answers; let main guides give what the page prints |
| SEO description with a percent sign ("up 4–6% in 2026") | Skipped as an unfilled template variable | Only skip real `%word%` variables |
| Excerpts starting with a byline or CSS | Shown as the summary | Prefer the search description; strip bylines and style text |
| `strip_tags` | Joins paragraphs without a space | Replace closing block tags with a space first |
| Password-protected published pages | Read and served publicly: WordPress asks for the password when the page is shown, while `the_content` on `post_content` and the SEO meta skip that check | Skip when the post has a password, in every reader (see "Security pass" below) |
| Loopback fetches | Follow redirects to any host, slow | `wp_safe_remote_get` with `redirection => 0` and a short timeout; follow redirects by hand only while they stay on the same host (see "Security pass") |
| Old dated content (past events) | Listed as current | Do not list undated or past items; ask the owner |
| A paragraph inside a list item | Read twice, once as the item and once as the paragraph | Read a paragraph only when it is not inside a list item, and only top-level list items |
| A list inside a list item, or right after text | Words run together ("statedHinges") | Put a space before a nested `<ul>` or `<ol>` when stripping tags |
| Small headings (`h5`, `h6`) | Their text merged into the section above, so exclusions read as coverage | Treat `h2` to `h6` as section headings |
| A heading that only says "Note" | Became a section of its own, and reads oddly as a question | Continue the section above it ("… Note: …") |
| A block every post carries ("Locations" with the showroom list) | Returned as a section of the guide | Skip such headings by name |
| Page-builder containers given the tag `header`, `aside` or `footer` | A rule that drops every `header` drops the page body | Drop only the site's own header and footer; inside the page's builder content these tags are containers |
| A price with cents ("$12.50") when price sentences are left out | The sentence was split at the point, so "50 per inch." stayed | A sentence ends at a full stop followed by a space or the end |
| A long post with 40 question headings | One guide was a tenth of the whole download | Pass on a fixed number of questions per guide (20), first in page order |
| A product type whose text lives in the page template and custom fields | The REST API gives the name and the terms, no content | Read the product's own page in the browser (`fetch`, `DOMParser`) from the builder's content container (`[data-elementor-type="single-post"]`); stop at "Related …"; skip price marks, buttons and placeholder text ("No description added", "test") |
| Text a builder prints without a paragraph tag (an info box) | A page of steps gave headings with nothing under them | Also read a `div` that has words of its own and no block inside it |
| A builder's fold-out FAQ on a page read as sections | Its questions and answers ran together under the heading above | Read each item as a question with its answer, and keep the fold-out's text out of the section it sits in |
| A closing call to action ("Are you ready…", "Get started today") | Returned as a section of the page | Skip such headings by pattern, and a gallery's heading too |
| A page with a title, one paragraph and a form | No headed section, so nothing was read | Read it as one section under its `h1` |
| Location pages with no schema of their own | Address, phone and hours are only in the page's text | Read the block under the page's own heading ("<City>, <ST> Location") and accept it only when an address, a phone number and at least five days of hours were found; otherwise the bundled copy answers, marked `source: bundled` |
| A custom post type named like a core one (`pages`) | Its REST address collides with the core route, so the browser cannot list it | Have the server put the list into the page's config |

Keep a fallback data file for facts another plugin normally supplies (locations, phones, hours), and re-check that file against the live site at each release: a fallback is exactly where a stale phone number hides.

### Page builders do not render inside wp-admin

Found in November 2026 in three plugins with the same structure. On one site it was seen live: the route flipped between a good and a weak reading of a page as the settings page was used. On the other two the pages at risk were found from outside and the fault was reproduced on the local test site.

- **What happens.** Elementor renders `the_content` in page requests and REST requests. On a wp-admin screen (not admin-ajax) it does not: the filter returns the plain copy Elementor keeps in `post_content`, which is the text of the widgets with their wrappers and class names gone.
- **How it reached visitors.** The plugin's settings page called the knowledge build to print a status line ("FAQ: 9 questions"). The build went into the ten-minute cache and the "last good copy". So each time the settings page was opened after the cache had ended, agents got the wp-admin reading for up to ten minutes. The install steps even said to open that page after every upload.
- **What the plain copy does to a reader.** Anything found by class name or wrapper is lost. A team page of flip boxes gave 0 people instead of 20. A financing section found by its container gave 0 options instead of 3. A fold-out FAQ came out as one block of text, or as no questions at all. A button's label ("Learn More") joined the sentence before it. Readers that use stored FAQ schema or plain headings and paragraphs gave the same result either way, which is why most pages looked fine and the fault went unnoticed.
- **The fix, three parts.**
  1. The settings page builds nothing. Its status lines are filled in by the browser with a `fetch` of the public knowledge route. WordPress treats a REST request without a nonce as a visitor's, so the page shows what agents really get, and that request also warms the cache after an upload.
  2. The cache function stores nothing on a wp-admin screen (`is_admin() && ! wp_doing_ajax()`): give that screen the last good copy, or a build of its own that is kept nowhere, and take no lock.
  3. When a builder page did not render (post meta `_elementor_edit_mode` is `builder` and the HTML has no `data-elementor-type=`), read the page as the site serves it instead of the plain copy.
- **How to check a live site from outside, read-only.** The REST API's `content.rendered` for a page holds `data-elementor-type=` when Elementor made it. The plain copy cannot be fetched, but it can be approximated: take `content.rendered`, drop the `div`, `span` and `section` tags, the scripts and the class attributes, and run the plugin's own parsers on both versions. Pages whose two readings differ are the ones at risk. Say that this is a reconstruction, not the stored copy.
- **What a live check cannot show.** Without wp-admin access you can confirm that the route's reading equals the tested parsers' reading of `content.rendered`. You cannot confirm that opening the settings page changes nothing, unless the owner opens it while you watch the route. That part rests on the local test. When the owner does open it, the visit proves something only if the ten-minute copy had ended before it and no request of yours rebuilt the copy first: note when you last asked the route.

### Security pass for a knowledge route

A security review of three live plugins (November 2026) found four points in the oldest one and none in the two built later. The rules were already in this guide. They had been added after the oldest plugin was built, and nobody went back to it. **When this guide gains a rule, check the plugins built before it.** None of the four leaked anything live; each needed one change on the site to matter. **Check against the whole guide, not one section:** that pass looked at the security rules only, and a later look found the same plugin still missing rule 8 (`retryable`), rule 15 (storage refused) and the start-once guard (section 1). The first two were fixed in its next release, the guard in the one after.

1. **Password pages, in every reader.** A helper `is_public( $post )` (published and `post_password` empty) is not enough if only one lookup uses it. There are three ways in: the lookup by address, the guide lookup for blog posts (`url_to_postid`), and the served-page fallback. When a page with a password is found, skip it. Don't treat it as "no post here", because then the fallback reads the page as served.
2. **The served-page reader stays on the site.** Use `wp_safe_remote_get`, which refuses addresses inside the host's own network, with `redirection => 0`. Then follow at most three redirects by hand, each hop again through `wp_safe_remote_get` with `redirection => 0` (resolve a relative `Location` against the current address first), only while scheme (http or https), host and port match `home_url()`, and carry the cookies each hop sets (`wp_remote_retrieve_cookies`). Plain `redirection => 0` with no hand-following broke a test site that answers a request without a cookie with a redirect to the same address: two pages lost their questions. A failed read is cached (an hour), so restart the test site after a broken run before testing again. Check the address against `home_url()` before the first request too, not only on a redirect: the addresses come from the site's own settings, but a filter in other code on the site can rewrite a permalink.
3. **The inline config is hex-escaped** (section 5). On WordPress 7.1 an unescaped config did not break the page: `wp_json_encode` already writes `/` as `\/`, so `</script>` came out as `<\/script>`, and core itself rewrote `<script` inside the inline script. Escape anyway (older WordPress versions, `<!--`, `&`). Test the printed page source, not the browser (section 8).
4. **The route reads only the section names it knows.** Intersect `?section=` with a fixed list. A request naming none of them builds nothing and gives the version alone; known names next to unknown ones give the known ones; no `section` gives everything. Before this, any unknown name loaded the whole knowledge, and `guides` plus a junk name built every section.
5. **Hiding a page reaches everything the plugin keeps of it.** A page set back to draft, made private, given a password or moved to the trash must stop answering from the knowledge and from the copy of the page as served (section 6, "A hidden page has no address"). Nobody outside can cause this, so it is not a way in. It is the owner's "hide" not being honoured for hours.

**Checking a live site from outside, read-only:**
- Password pages: `/wp-json/wp/v2/pages?per_page=100&_fields=link,content.protected` lists them (3 on one site, none of them read by the plugin).
- Redirects: request every address the plugin reads with redirects off. All 35 answered 200.
- Route names: ask with a plain unknown name (`?section=nonsense`). Values that look like an attack (`<script>`, `../`) get a 403 from the host's firewall, which tests the firewall, not the plugin.
- The WordPress version is usually hidden; say so rather than guess whether core already covers point 3.

The sessionStorage hand-off and the form tools, checked in the same review, were fine. The things worth checking there: the hand-off expires, is deleted on arrival and holds only what the visitor typed, and no tool submits.

## 4. Topic map for high-intent questions

A small data file of topics (id, label, intent, real search queries from Search Console, one main guide path, related paths) lets a `find_guide` tool route a question to the page the site is building up.

- Pick each guide by real data: the strongest page by US clicks, or the page the content programme is targeting.
- Leave out pages that are visibly stale (an old year in the title) until they are rebuilt.
- Read title, summary, modified date and FAQ live; drop a topic whose page is unpublished.
- Matcher that worked: content words with synonyms (price→cost, renovation→remodel), require min(3, 60%) of the question's words, bonus for a phrase match, penalty for label words not asked, and require a subject word.
- In article search, put the main guide first. Only blog-post guides go into the article list; service pages stay in a separate `main_guide` field. Flag that on the server (`article: true`).
- Upkeep: when a guide is merged or redirected, change its path in the data file and ship a new version.
- Finding what to add next: group 90 days of US Search Console queries by intent (catalog and price list, warranty, contractors, product lines…), then ask the live tools the top real queries of each group and list the ones that get "no guide". A page high in clicks with no topic is the clearest miss. Do not add a topic whose only page gets no impressions for it: say so and leave it out.
- A policy page written as headed sections (warranty, returns) has no questions: read each heading with the text under it as one answer, flagged per topic in the data file, and leave out the footer, forms and pop-ups.
- A catalog or price-list request is its own journey step: give it a form tool, and point price questions to it instead of quoting figures.
- A guide with no FAQ can be read as sections the same way. A page with no headed sections gives nothing to read: the topic then returns its title, summary and links. Say so plainly; it is not a fault to report in the page.
- **Every listed query must reach its own topic.** Test all labels and queries against the matcher (201 on one site). Three real queries made only of shared words ("types of kitchen cabinets") matched nothing. Fix that worked: a question reaches the topic when a whole listed query is in it and it has no word from outside the topic; "kitchen cabinets" alone still matches none.
- Search Console has the queries people type into Google, not the plain questions they ask an assistant ("how long is the warranty", "is the warranty transferable"). Add those to the topic and mark them in the data file as not from Search Console.

### A policy topic (warranty, returns)

- **Quote, do not summarize.** A 370-character cut stopped a warranty answer before its term ("5 years … non transferable" sat near the end of the section). Give the section that answers best whole, with the server keeping each section under a fixed length.
- **Name the other sections.** Return their headings in a short list (`other_sections`) so the agent can ask again for "exclusions" or "claims". Two more sections cut to stubs cost more room and say less.
- **Rank sections by the words that tell them apart.** Every section of a warranty says "warranty", so that word picks nothing. Count only the question's words that appear in some sections but fewer than half ("claim", "void", "exclusions").
- **Guard the topic.** It answers only a question that names it ("warranty") and no other topic's brand or product. Without the guard, "how long is the Brand X warranty" (another brand the site sells) returned this brand's warranty. The cost: "does Product Y have a warranty", where Product Y has its own topic, gets no guide either and falls to the FAQ tool. Put that trade-off in the README.
- **Next step:** read what the page says to do (email the documents) before writing "call the showroom".
- The owner may not want dollar figures passed on at all: a shortened answer can lose the sentence that says "ranges, not quotes". Offer the choice (a price note beside the figures, or leave such answers out and point to the page and the showroom) and encode the answer.

## 5. Page speed

Aim: zero cost where there is no WebMCP.

- Print one small inline script in the footer: the config plus a loader. Browsers without the API download no file from the plugin.
- With the API present, load one minified file after the load event, when the browser is idle.
- No stylesheet. Inject the few banner rules when they are needed ("Remove Unused CSS" would strip a stylesheet anyway).
- With WP Rocket "Delay JavaScript" on, add only the inline loader to `rocket_delay_js_exclusions`. Leave heavy widgets delayed and start them on demand from the tool.
- Start-up calls stay at the **end** of the script file. A late-loaded file that calls a function before its `const` tables are defined throws.
- Escape the inline config with `wp_json_encode( $config, JSON_HEX_TAG | JSON_HEX_AMP )`, and keep it small (move long lists into a fetched JSON file).
- Minify with a pinned tool and target (for example `esbuild@0.24.0 --minify --target=chrome116`) so a rebuild is byte-identical.

**Speed-test trap:** an address with a query string the cache plugin does not know (`?cb=1`) gets a raw page with no optimisation, and scores far lower (a home page scored about 60 points lower that way than on the clean address). Test the clean address, or use a known tracking parameter such as `?utm_source=speedtest`.

## 6. Caching (wp-admin access only)

Plan so nothing ever needs a CDN purge.

- **Pages:** typically cached about 10 minutes at the host and the CDN. After an install or a settings change, clear the caches available in wp-admin and wait.
- **Static files:** cached for a long time, so put the file's modified time or version in its address. A new version means a new address.
- **Knowledge route:** transient (10 minutes), cleared on `save_post`, sent with `Cache-Control: public, max-age=600`.
- **Rebuild lock:** without one, every request arriving when the cache expires rebuilds everything at once. Set a short lock transient, serve the last good copy (kept in a non-autoloaded option) to the others, then store the new build. Store the plugin version in the cached copy and rebuild when it differs. One exception: right after an update, while one request holds the lock, give the others the copy the version before left (it has the same shape) instead of letting each of them read every page.
- **Nothing built inside wp-admin is stored.** A page builder does not render there, so a build made by a settings page is a weaker reading (section 3). The settings page asks the public route from the browser instead; opening it after an upload still warms the cache, through that request.
- **Build only what was asked:** a request for one section should not build all of them, and a request naming no known section should build nothing (section 3, "Security pass").
- **Clear a served-page copy on save, and expect clearing alone to fall short.** Pages read as the site serves them are kept longer (12 hours). Clearing only the knowledge on `save_post` left answers read from such a copy as before the edit for half a day. Drop the edited post's copy as well. But the plugin's request goes through the site's page cache and CDN (about 10 minutes on one site), so a rebuild right after the edit can fetch the old page and keep it 12 hours more. Set a mark for 20 minutes, named by the page's path so every form of its address finds it, and keep copies fetched under the mark 15 minutes. Worst case after an edit is then about 40 minutes. Keep the copy's own name the same across versions, or the first build after an update fetches every served page again.
- **A hidden page has no address to look its copy up by.** On `save_post`, `get_permalink()` of a page set back to draft or moved to the trash gives `?page_id=12`, not the address the page was served at. So the copy of that address stayed its 12 hours: the one copy that still showed the page as it was while public. Hook `post_updated` as well and, when the post was published before the save, drop the copy of `get_permalink( $post_before )`; this covers a renamed page too. Drop every form of the address the readers ask for (the permalink, `home_url( $path )` with and without the closing slash) in one helper, and set the edit mark there. Try it in a real WordPress, because it rests on how WordPress names a draft's address: a switch in the test site that makes a page, stores a copy, sets the page to draft and reports what is left. In the stubbed parser test, make `get_permalink` answer like WordPress (no public address unless published), or the save alone passes.
- **Settings printed on every page** (topic labels read from a file, the blog address) belong in the cached part of the config.
- **After an upload, wait about 20 minutes before testing.** On a managed WordPress host behind a CDN the home page showed the old version for about 9 minutes and a plain REST address for about 20 (it was renewed once with the old copy). Any extra query parameter on the REST address returns fresh data at once. Failed checks in that window are the cache, not a bug. Better than waiting blind: the knowledge route answers with the new version at once, while the saved home page keeps the old config for 5 to 10 minutes. Ask the plain home page once a minute until its config carries the new version, then start the after-install check. Ask the clean address the test loads: the same page with `?utm_source=` is built fresh and showed the new version while the clean address still served the old one. A run started then failed one version check and skipped the new version's checks. One lookup in that run answered "could not be reached" during the first knowledge build after the upload. The same lookup answered in under half a second minutes later, so run again before calling it a fault. All of this happened again after the next upload: the route gave the new version at once, the saved home page kept the old config about 10 minutes (the CDN reported `HIT`, `Age` up to about 570 seconds, then `EXPIRED`), and the first run again had one lookup answer "could not be reached". Expect it. When polling the home page, read the version from the plugin's own inline config: the first `"version"` on a page can belong to another plugin.
- **An upload that did not take looks like a slow cache, and waiting does not fix it.** More than once an owner reported the upload and the site kept answering the old version for hours. Tell the two cases apart with one request: ask the knowledge route with a query string never used before. No saved copy can answer that, so an old version there means the plugin files were not replaced. Two more signs: the tools file on the server is still byte for byte the old build, and its `?ver=` stamp, when the stamp is the file's modification time, still shows the old date. Before telling the owner, rule out your own side: the zip's top folder and version header are right, and the zip did not land on a sister site (ask each site for the other plugin's file; 404 is the good answer). The usual causes are then the "Replace current with uploaded" step not confirmed after "Install Now", or an upload to a staging copy. Ask which version the Plugins screen shows. After a second upload the sites answered with the new version within three minutes and passed the after-install check.
- Add an `uninstall.php` that removes the cache options and transients; keep the settings (the token) on purpose.

## 7. Origin-trial token

The trial needs no API key. Each browser's trial issues a token for one origin, and the page hands that token to the browser; without it, Chrome and Edge expose the tools only where the test flag is on. Chrome and Edge run separate trials with separate tokens. Getting them (checked 26 Nov 2026):

1. **Chrome:** open the [WebMCP trial registration page](https://developer.chrome.com/origintrials/#/register_trial/4163014905550602241) (or find WebMCP under [Active Trials](https://developer.chrome.com/origintrials/#/trials/active) and click Register), sign in with a Google account and enter the origin. Chrome's guide says origin trials "are public and open to all developers".
2. **Edge:** open the [Microsoft Edge WebMCP trial](https://developer.microsoft.com/microsoft-edge/origin-trials/trials/0b76fe60-b266-458e-a285-04e375c0c31a), sign in with GitHub and enter the domain. That page lists 29 March 2027 as the trial's expiry date.
3. **Put each token on every page that registers tools:** `<meta http-equiv="origin-trial" content="TOKEN">` in the `<head>`, or an `Origin-Trial: TOKEN` response header. Both browsers document both ways.
4. **Renew:** Chrome emails a renewal link when a token expires, and when a trial is extended it asks for a new token for each origin (My Registrations, Renew, then copy the new token onto every page). Chrome ignores invalid or expired tokens, so after expiry the tools are gone for visitors: track the expiry date (see below).

Rules from the builds:

- Register the exact origin the site serves (`https://www.example.com`), subdomain matching on if needed.
- **Do not tick "third-party matching".** A third-party token in a plain meta tag is rejected with status `WrongOrigin`.
- Give the settings field one token per line and print one meta tag each (Chrome and Edge trials have separate tokens).
- Check the result with the DevTools protocol (`Page.getOriginTrials`): the trial should read Enabled, the token Success. Then confirm in a browser started **without** the flag.
- Note the expiry date and renew before it. A token can be read without the console: it is base64 of one version byte, 64 signature bytes, four length bytes and a JSON text with the origin, the feature and the expiry. A small script that prints these (never the token itself) and then starts each installed browser without the flag settles "is the token right" in a minute.
- After the token is saved, a CDN can keep each page's old copy for its cache time (10 minutes on one site): a page without the tag while the same page with `?utm_source=x` has it means wait, not clear again.
- Once a token is on the page, a test browser has WebMCP without the flag. Run the whole after-install suite once that way (what a visitor's Chrome does), and start the "browser without WebMCP" check with `--origin-trial-disabled-features=WebMCP` so it still runs.

## 8. Testing ladder

Run the cheap steps first; each catches different things.

1. **Parsers without WordPress** (seconds): load the PHP file with stubbed WordPress functions (transients, options) and run fixtures through it.
   - **The tools file without a browser** (seconds): run the script in Node with a stand-in `document.modelContext`, `window`, `location` and a `fetch` that returns saved knowledge. It checks what needs no page: every listed query reaches its topic, description and name sizes, the largest answers on worst-case pages, and, with a saved copy of the live knowledge route, the size and shape of every real answer.
2. **Every tool in real Chrome on a local copy** (about a minute): puppeteer-core with the installed Chrome, a temporary profile and `--enable-features=WebMCP`; headless works. A WordPress Playground site seeded with test content is enough. In a browser without the flag (Firefox, WebKit, the Claude Browser pane, Chrome without `--enable-features=WebMCP`), load `@w3c/webmcp-polyfill` in the test page before the tools file. It gives the `Tool` objects expected in Chrome 160, `outputSchema` included, so the test scripts can be tried on that shape before Chrome 160 ships. Tried on 24 Nov 2026 with one reference build (Chrome 158 without the flag, recorded site answers): the same 15 tools and the same 20 answers as native Chrome 158, and the answer-shape check's "getTools() gives the schema as registered" branch ran and passed. Where it differs from Chrome 158: the owner is `source`, `outputSchema` is shown (`null` when absent), and `structuredClone(tool)` works instead of throwing. It does not replace the run in real Chrome. It has no declarative forms, so a page that uses them still needs its own test stand-in.
3. **New build against live content before upload:** in the test browser only, intercept the request for the live tools file and answer with the local build. Compare old and new answers for the same questions.
4. **After install, the live site as it is:** nothing injected, non-GET and third-party requests blocked, nothing submitted. Gate new checks on the version the site reports, and confirm the live file is byte-identical to the build.
5. **Ask real customer questions:** 50 to 60 questions as a customer would word them, read every answer in full, fix the weak ones. This found more than any unit test.
6. **A blind agent:** let a separate agent with no knowledge of the code serve a few pretend visitors through the live tools, and read where it struggled.
7. **Evals** (webmcp-evals): give each expected call a `mockOutput` in local mode or the model loops on the empty result.
8. **PageSpeed Insights** before and after, on the clean address.

Lessons about the tests themselves:

- A check that cannot fail is not a check. Run each new check once against the old code and see it fail. Watch for conditions like `!x || …` that pass when the thing is missing.
- Check position, not only presence ("main guide is first", not "main guide is in the list").
- Wait for the full tool count before testing: a tool that registers after a fetch arrives last.
- Local Playground servers can redirect-loop clients without cookies; check readiness from a browser, and fetch with `cache: 'no-store'` after a restart.
- A CDN may block plain script fetches of pages while the REST route stays reachable; use a real browser for pages.
- Built-in browser panes may have no WebMCP at all. Test in real Chrome.
- Anything added to an answer after it was fitted to the size budget (a "more details on the page" note) can push it over. Add it before fitting, and test every item, not one sample: one door style of 33 was 11 characters over.
- A partial match needs a floor (half of the question's words): one shared word of a long question is noise.
- Keep published numbers honest: test that a calculator's high value does not exceed the published maximum, not only the midpoint.
- **A pre-install test must own its config.** Once a version is installed, the live page prints its own config after the test sets one, and the local tools then read the installed knowledge. Two defects passed that way. Pin it (`Object.defineProperty(window, 'config', { value, writable: false })`), block the installed tools file and the installed knowledge route in the test browser, and assert that the knowledge came from the test's address.
- **Make the fixture as long as the live page.** The test site's warranty section was short, so a cut at 370 characters lost nothing there and lost the term on the live page. Copy the live structure: section lengths, where the key sentence sits, the stray "Note" heading.
- **Make one test page a builder page.** A test site of plain posts renders the same everywhere, so the wp-admin fault (section 3) could not show. Imitate the builder: keep the real markup in a meta field and return it from a `the_content` filter except on wp-admin screens, put the plain copy in `post_content`, and block same-site requests from wp-admin so the worse case is tested. Then build once inside wp-admin and check that the build reads worse there, that nothing was stored, and that the route still gives the good reading after the settings page was opened. On the old code five of nine such checks failed.
- **Write the after-install check before the first upload and run it the same hour.** On one build four suites were green before upload, and the after-install check then found a fault in each of the first two releases on the first day. It is the only step with the real server (the page builder, the cache, a settings page being used), the real third-party scripts, and time passing.
- **Compare the live server's reading with the tested parsers on the same input.** For a page read as sections, the server reads the page's content, not the whole served page: give the tested parsers the REST API's `content.rendered` and require every heading and text to be equal. (Read from the full served page, one guide had a section more, from the template.) For a blog guide compare the number of answers only: the stored schema can word a question differently from the page's heading.
- **Pace a live test.** About 170 requests in three minutes got HTTP 429, and a browser started right after was shown a check page where no tool registered. Keep a third of a second between requests and a second or two between pages, wait 45 seconds and ask again when a tool answers "busy", and print how often that happened. Do not run the dry run and the after-install check back to back.
- **A tool's shorter answer under load is not a fault.** When a product page could not be read, the tool gave the listing facts and pointed to the page. A check that sees "no details" asks once more after a pause before it fails.
- **Third-party scripts change the page after it has loaded.** Let the ones a tool touches run in the test (the embedded form, the robot check), wait a few seconds, then call the tool again. Locally, imitate what they do (move the frame into a new box) so the check does not depend on timing.
- **Not every POST is a form.** Cloudflare posts to `/cdn-cgi/challenge-platform/` from every page. Let those through and do not count them, or "no form was sent" fails on a page where nothing was sent.
- **Give the live check switches for the day's real needs:** the server part alone (a minute, no browser), the version the site is expected to run when it is not yet this folder's, a browser without the flag once a token is in, and the local tools file in place of the site's.
- **Test what must not match.** For every new query added to a topic, add the neighbours that should stay out (another brand's warranty, "hinges" alone).
- **In an update dry run, two versions are in play:** the installed server and the new tools file. Keep both in the test (`LIVE_VERSION`, `TOOLS_VERSION`), gate each check on the one it depends on, and where the new parsers differ from the installed server on purpose, list those differences in the check instead of letting it fail.
- **An independent review finds what the author's tests share a blind spot with.** A code review of one release found an answer cut before its key sentence, plain questions that matched no topic, and the stale pre-install test that had let both through. Its second reviewers then found two flaws in the first fixes by asking real questions: a wrong section ranked first, and another brand's question matched.
- When a review note depends on the site ("add handles, if the accessories page lists hardware"), read the page first. It listed none, so the words were not added; what it did list was. The same goes for a change found in someone else's copy of the plugin: a FAQ-reader change (skip headings in forms and builder pop-ups) was checked against the live route first. Its 431 answers on 35 pages had no such text, so the change was left out.
- **A browser check can pass on the old code because WordPress did part of the job.** A test that read the config in the browser passed on unescaped code (core had already rewritten `<script`). A check of the printed page source (the config text has no raw `<` or `&`, and carries `\u003C`) failed on the old code as it should.
- **Make the HTTP stub behave like WordPress.** In the parser test, a stub for `wp_remote_get` that never redirects would pass a reader that follows redirects anywhere. Script the responses, follow `Location` unless `redirection` is 0 as WordPress does, and record which function was called and with which options.
- **Give the test site the cases a review asks about:** a published page with a password, an address that redirects to another host (on a local site, the other loopback name: `localhost` when the site is `127.0.0.1`), and a config value carrying `<!--<script>` and `&`. On the old code six Chrome checks and eight of eleven parser checks failed. The other three checked behaviour kept on purpose: an open page is still read, a known section next to an unknown one is still given, and the route is still cacheable.
- **Refuse session storage the way Chrome does.** In the test page, before calling the tool: `Object.defineProperty(window, 'sessionStorage', { configurable: true, get() { throw new DOMException('Access is denied for this document.', 'SecurityError'); } })`. Check the answer (`stored: false`, empty `will_fill`, every field still needed) and that the next page opens empty with nothing posted. Run the same in the after-install check on a tab of its own, gated on the version. On the old code 4 of 7 such checks failed; the other 3 check what stays the same (the page opens empty either way; with no details the answer is the plain one).
- **Make the transient stub record the cache time,** so keep times (12 hours, 15 minutes after an edit) are tested, not only whether something was stored.
- **Scripts that run rarely go stale.** A live dry run still counted 8 event titles five versions after the tool stopped listing them, and failed on that alone. When an answer changes shape, search every test script for it, not only the main suite.
- **Run the new checks on the old version's files.** Parsers: let the test take the plugin folder from an environment variable, point it at the unzipped previous zip, and put `function_exists` around functions the old version lacks. Chrome: copy the previous zip's files over the mounted plugin folder, run, and put the new files back in a `trap`; then compare the minified file's hash with the one in the new zip. On one release 11 of 16 new parser checks and 7 of 9 new Chrome checks failed on the old files; the rest checked what holds either way.
- **An error the code catches hides from "no page error".** With the tools file included twice, the old code raised no page error and kept the same number of tools: Chrome refused each duplicate tool and the file only warned. Count the plugin's console warnings.
- **A page of the site shown in a frame is a real case.** On the old code the framed page downloaded the tools file, and its tools joined the list of the page around it. Check both: the frame starts nothing and downloads nothing, and the page around it keeps its own count.
- **A dry run through the after-install check** (`--local-tools`: the test browser gets the local tools file in place of the site's) has two versions in play, like any update dry run. A check depends either on the tools file or on the loader and config, which are still the installed version's. Gate each on its own part and print what stays as it is until the upload (the frame still downloads the file once; the file then starts nothing).
- **Equal file sizes do not show that a file was not rebuilt.** A minifier drops comments, so a release that only changes the version comment gives a byte-identical minified file. Compare the served file with the build by hash, and look for a text the new code added.

- **Test an `outputSchema` with every kind of answer, from recorded responses.** In real Chrome, on a stand-in page at the site's own address (request interception), call each tool for every answer it can give: products found, nothing found, each refusal, several matches, and the site down (a fresh page where the site answers 503). Validate with Ajv in strict mode. Record the site's responses once with GET only and replay them on later runs, so the check repeats exactly and puts no load on the site; where headless browsers are turned away, write the responses by hand after the fields the tools read. Add made-up wrong answers that must fail (a required field missing, a number where text is promised, an answer that is both a result and an error), or a schema that allows anything still passes. Run it on the minified file too.

## 9. Release checklist

- [ ] Version bumped in every place it appears (plugin header and constant, script header).
- [ ] Minified file rebuilt after the last source change.
- [ ] Parsers test and local Chrome test pass; new checks were seen failing on the old code.
- [ ] New build tried against live content (step 3) for the questions the change is about.
- [ ] Fallback data file compared with the live site.
- [ ] Nothing on a wp-admin screen builds or stores the knowledge; the settings page reads the public route.
- [ ] Security pass (section 3): password pages skipped in every reader; the served-page reader is the safe request and stays on the site; the inline config is hex-escaped and checked in the page source; the route reads only known section names.
- [ ] A page that is hidden (draft, trash, private, password) stops answering from every stored copy; tried in a real WordPress.
- [ ] Tool-use events, when the plugin sends them: no event holds anything asked or typed; answers are equal with the events off; the owner has the Tag Manager steps.
- [ ] For a plugin built before the guide's latest rules: every rule in section 2 and every trap in section 3 checked against its code, not only the security pass.
- [ ] Every listed query reaches its topic; descriptions, parameter descriptions and names are within Chrome's sizes; the largest answer is within the budget.
- [ ] Hints: read-only tools marked `readOnlyHint: true`; hand-offs carry no hint; any tool whose answer quotes visitors carries `untrustedContentHint: true`; no hint is written as false.
- [ ] A tool that declares `outputSchema`: every real answer (good, empty, failed) validated against it, the failed one through its `oneOf` error branch.
- [ ] If the change makes answers shorter, the owner has seen what is lost and chosen.
- [ ] Zip built from a script, stray files excluded; older zips kept.
- [ ] README says what changed, in plain words, and which zip to install.
- [ ] The after-install check exists before the first upload.
- [ ] After upload: caches cleared in wp-admin, wait until the saved home page carries the new version (up to about 20 minutes), after-install test, live file compared with the build.
- [ ] One fix, one small version: the README says what agents got while the fault was live.
- [ ] Nothing was submitted and nothing on the live site was changed by the tests.

## 10. Working with the site owner

- **Review the tool, not the site.** Take the site's content as given. Do not hand over a list of faults in their pages unless asked; fix the tool so it reads the page correctly.
- **Check before saying something is missing.** Look at the page's own meta description, schema and markup before reporting that a field does not exist. The tool's reader is the more likely culprit.
- **Respect hand edits.** If the owner edited a data file by hand and chose to keep it, do not run a refresh script over it or suggest reverting it.
- **Ask about judgement calls** (old events, warranty wording that depends on the project) and encode the answer as a rule, for example "warranty depends on the project: point to the consultation".
- Give every instruction as a wp-admin step when that is the only access. Write for a non-developer.
- **Give every command with its folder** (`cd <plugin folder> && node test/live-after-install.mjs`). A test path given on its own was run from the parent folder and stopped at once with "Cannot find module".
- **When a requested change costs something, do it and show the cost.** Lowering the answer limit to Chrome's 1,500 characters was asked for and applied; the owner got a before-and-after table (answers per guide, detail lines per product, articles per search) and the one-number way back, and chose to keep it.
- **Report a fault in your own release the same day:** what it was, what agents got while it was live ("nothing false, but one answer was no longer its own"), how it was found, and the zip that fixes it. Say also what the live check could not prove.
- **A copy of the plugin made elsewhere** (another agent, another folder) can start from an old version and reuse a version number already shipped: one took the number of the release before the live one, and was built from a release older still. Compare its files byte by byte with the old zips to find its base, never upload it, and run the tests on it (they stopped at a function its base did not have). Take the useful changes and rewrite them on the current version. Its code may be copied from a sister plugin (one was, word for word), so check the sister for the same flaw. Tell the owner which changes were taken, which were left out, and why.
- **A review from another tool: check what it reviewed before acting on it.** One report had audited a copy two versions old and a zip that was never the live one. Of its twelve points, several were already done in the live versions, two were wrong (one read equal file sizes as "not rebuilt", one said a zip was missing that was in the project folder), and the rest were small and real. Download what the site serves, compare it byte for byte with the build, run the plugin's own tests on each claim, and answer point by point: already fixed, wrong, or real, with its size.
- **When a fix is put off as low-risk, try the risky case before saying what the fix will close.** A fix was held on the word that it stops a hidden page answering from its stored copy. Built and tried in WordPress, the design it was to be copied from did not cover a page set back to draft. Say so the same day, with what the live version still does until the upload.
- **Say where a note was not followed to the letter, and why,** in a short list: kept three queries instead of dropping them, one guide read as sections instead of two, no hardware words because the page lists none.
